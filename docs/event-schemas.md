# CI/CD Event Schemas

## Purpose

This document defines the provider-facing webhook contracts and the provider-neutral event envelope used by the control plane.

Provider payloads are untrusted input. Parsing them must never execute embedded instructions, interpolate values into commands, or pass raw payload text to an AI model.

## Supported providers in Phase 3

Phase 3 supports simulated payloads shaped after:

- GitHub Actions workflow and deployment events.
- Jenkins build and deployment events.

The implementation uses project-owned schemas rather than claiming complete compatibility with either provider.

## Signed webhook request contract

Each webhook request includes:

| Field | Location | Required | Rule |
|---|---|---:|---|
| Event source ID | Path | Yes | UUID owned by the authenticated project configuration |
| Delivery ID | Header | Yes | Provider-scoped opaque identifier, 1â€“200 characters |
| Event type | Header | Yes | Provider event type, 1â€“100 characters |
| Delivery timestamp | Header | Yes | RFC 3339 UTC timestamp |
| Signature | Header | Yes | `sha256=<lowercase hexadecimal HMAC>` |
| Content type | Header | Yes | `application/json` |
| Payload | Body | Yes | UTF-8 JSON within the configured size limit |

The server verifies the signature over the exact received request bytes. JSON must not be parsed or re-serialised before signature verification.

## Required envelope fields

- `schemaVersion` identifies the internal schema contract.
- `eventId` is generated by the platform after successful verification.
- `organisationId`, `projectId`, and `eventSourceId` establish tenant ownership.
- `deliveryId` supports idempotency and auditability.
- `provider` identifies the adapter that produced the record.
- `eventType` uses a stable internal enum.
- `occurredAt` is the provider event time.
- `receivedAt` is the control-plane receipt time.

## Normalised event types

Phase 3 defines:

- `PIPELINE_RUN_STARTED`
- `PIPELINE_RUN_COMPLETED`
- `PIPELINE_JOB_STARTED`
- `PIPELINE_JOB_COMPLETED`
- `DEPLOYMENT_STARTED`
- `DEPLOYMENT_COMPLETED`

Unsupported provider event types are recorded as rejected deliveries and are not converted into normalised events.

## Pipeline status values

- `QUEUED`
- `RUNNING`
- `SUCCEEDED`
- `FAILED`
- `CANCELLED`
- `SKIPPED`
- `TIMED_OUT`
- `UNKNOWN`

Adapters must map only explicit provider evidence. Missing or unfamiliar values map to `UNKNOWN`; they must not be guessed.

## GitHub Actions-style payload minimum

The simulator requires:

- workflow-run identifier
- workflow name
- run attempt
- status or conclusion
- event timestamp
- repository identifier
- commit SHA
- Git ref

## Jenkins-style payload minimum

The simulator requires:

- build identifier
- job name
- build number
- build status
- event timestamp
- source revision when available
- environment or deployment target when available

## Validation rules

- JSON nesting depth is bounded.
- Request body size is bounded.
- Strings have explicit maximum lengths.
- External identifiers remain strings and are never trusted as database identifiers.
- Provider timestamps outside plausible bounds are rejected.
- Tenant identifiers come from the configured event source, never from the payload.
- Unknown JSON properties may be ignored by adapters, but required fields must be validated.
- Raw secrets, credentials, environment dumps, and full logs are not copied into the normalised envelope.

## Schema evolution

Breaking changes require a new `schemaVersion`. Additive optional fields may remain within the same version when older consumers can safely ignore them.
